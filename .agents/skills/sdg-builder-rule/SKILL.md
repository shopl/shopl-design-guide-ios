# iOS SDG 컴포넌트 프로퍼티·공개 API와 구현 규칙

기존 코드와 관련 PR에서 확인한 공통 패턴을 바탕으로 한 작업 기준이다. 기존 코드 전체가 이 규칙을 준수한다고 해석하지 않는다. 주석·버전의 상시 작성은 2026-10-19 사용자 요청으로 추가한 규칙이며, 기존 코드에서 일관되게 지켜지던 관례와 구분한다.

새로 만들거나 이번 작업에서 수정하는 코드에 적용한다. 규칙 적용만을 이유로 무관한 컴포넌트·API·파일 구조를 일괄 변경하지 않는다. 작업 경로의 지침과 최신 합의 요구사항을 함께 확인한다.

## componentProperties와 공개 API의 대응

- 디자인 설정에 관한 공개 API의 기준은 Figma 사용자가 컴포넌트 인스턴스의 프로퍼티 패널에서 선택·제어하는 `componentProperties`다. 공개 API 전체를 이 목록으로 제한하지 않는다. 기능 화면을 구현하는 사람이 가이드 페이지를 매번 열지 않아도 디자인의 설정과 코드 입력을 연결할 수 있어야 한다. 코딩 에이전트도 디자인의 선택값을 실제 API에 매핑해야 하므로 같은 대응 관계를 유지한다.
- 대상 디자인 버전의 컴포넌트와 인스턴스를 식별하고, 노출된 프로퍼티의 이름·타입·선택지·현재값을 확인한다. 인스턴스에 설정된 현재값과 원본 컴포넌트의 정의·기본값은 구분한다. 선택된 프레임의 레이어 목록만으로 컴포넌트 프로퍼티를 확인했다고 판단하지 않는다.
- MCP가 반환한 생성 코드의 props·인자·기본값은 보조 근거다. 원본 프로퍼티 정의나 전체 선택지를 그대로 반환한 것으로 간주하지 않는다. 필요한 계약을 확인할 수 없으면 확인된 항목과 미확인 항목을 구분해 사용자에게 확인을 요청하고, 미확인 값에 의존하는 API를 추측해 구현하지 않는다.
- 공개 입력은 확인된 프로퍼티의 이름·의미·선택지·독립적인 제어 범위와 대응시킨다. `Show Face` → `showFace`처럼 Swift 표기 관례는 적용할 수 있다. 공개 Model의 프로퍼티와 초기화 함수로 전달받는 것도 API 노출이다. 컴포넌트 View의 initializer에 모든 값을 개별 인자로 나열할 필요는 없으며, 묶인 입력에서도 개별 프로퍼티의 대응과 제어 가능성을 유지한다.
- 가이드 페이지의 실제 섹션·상태·규격·동작 설명도 읽어 구현 세부와 제약을 보완한다. Anatomy, Spec, Style, State 등은 예시이며 분석 범위를 고정하지 않는다. 섹션 제목이나 시각 요소라는 이유만으로 같은 이름의 공개 입력을 만들지 않는다.

| 가이드 항목의 성격 | 코드 반영 |
|---|---|
| componentProperties에 노출된 선택·제어 항목 | 이름·의미·제어 범위가 대응하는 공개 입력 제공 |
| 가이드에서 고정으로 정의하고 외부 제어가 필요 없는 항목 | 가이드 용어와 연결되는 내부 프로퍼티로 정의 |
| 선택한 크기·상태 등에 따라 결정되는 규격 | 해당 입력으로부터 계산하는 내부 프로퍼티로 정의 |
| 구현에 필요한 데이터·콜백 | 디자인 프로퍼티에 더해 필요한 공개 계약 제공 |

- 프로퍼티로 정의할 것인지와 공개 API로 노출할 것인지를 구분한다. 고정 항목도 동료가 정의 위치와 적용 값을 확인할 수 있어야 한다. 값은 저장·계산 프로퍼티로, 시각 요소는 필요한 경우 계산 View 프로퍼티로 표현하고 기존 디자인 토큰을 재사용한다. 조회 결과에 프로퍼티가 없다는 사실만으로 고정 항목이라고 단정하지 않는다.

## Model의 역할과 템플릿 조합

- 컴포넌트의 Model은 해당 컴포넌트를 구성하는 입력값을 한 단위로 전달하기 위한 타입이다. 식별자·텍스트·이미지 URL 같은 데이터뿐 아니라 외부에서 선택하는 크기·스타일·표시 상태·아이콘·색상 등 필요한 디자인 설정도 함께 담는다. Model을 서버 데이터나 콘텐츠만 담는 타입으로 한정하지 않는다.
- 템플릿이 하위 컴포넌트의 설정을 그대로 허용하면 하위 Model을 보유하거나 입력으로 받아 재사용한다. 이 경우 같은 설정을 템플릿의 개별 필드로 반복 나열하고 호출자가 다시 조립하게 만들지 않는다. 입력을 묶는 목적을 모든 템플릿에서 하위 Model을 직접 주입받아야 한다는 요구로 해석하지 않는다.
- 템플릿의 componentProperties나 가이드가 하위 컴포넌트보다 선택 범위를 좁히거나 값을 고정하면, 템플릿 전용 Model·선택 타입으로 허용된 입력만 받고 내부에서 하위 Model을 구성한다. 데이터와 필요한 디자인 설정을 묶는 원칙은 유지한다. 예를 들어 Avatar의 Small·XSmall만 허용하는 템플릿은 해당 두 선택지만 가진 Size를 받아 내부에서 SDGAvatar.Size와 Model로 변환한다.
- 디자인 설정·데이터·동작의 구분은 각 입력의 의미와 책임을 설명하기 위한 것이다. 서로 다른 initializer 인자나 데이터 전용 Model로 반드시 분리하라는 뜻이 아니다. 콜백·Binding을 Model에 포함할지는 기존 호출 계약과 상태 소유권·수명을 함께 확인해 정하며, 입력을 묶는다는 이유만으로 일괄 이동하거나 제외하지 않는다.
- 가이드에서 고정되거나 다른 입력에서 계산되는 내부 값까지 Model의 외부 설정으로 옮기지 않는다. 템플릿의 고정값·허용 선택값이 하위 Model에 어떻게 반영되는지 명시한다. 새 입력을 설계할 때 완성된 하위 Model과 같은 설정의 별도 인자를 함께 받아 덮어쓰는 구조를 만들지 않는다. 설정의 기준을 한 곳에 두어 템플릿 제약을 우회하거나 값이 충돌하지 않게 한다.
- 예를 들어 기존 `SDGCheckBox.Model`은 크기·선택 색상·상태를 담고, `SDGCheckBoxLabel.Model`의 `box`가 이를 보유해 하위 컴포넌트에 전달한다. 이는 입력 조합의 참고 사례이며 특정 필드명·기본값을 다른 컴포넌트에 복사하는 규칙은 아니다.

## 가이드와 componentProperties의 우선순위

- 가이드 페이지와 componentProperties가 같은 설정을 다른 이름이나 분류로 설명해 모호한 중복이 생기면, 확인된 componentProperties의 이름과 정의를 우선한다. 이 경우 사용자에게 판단을 다시 요청하거나 디자이너 확인을 기다리며 구현을 보류하지 않는다.
- 예를 들어 Avatar 가이드의 `Spec`과 componentProperties의 `Size`가 같은 크기 설정을 뜻하면 공개 API는 `Size`·`size`에 대응시킨다. 가이드 페이지의 상세 규격은 이 입력의 구현 근거로 활용하며, 중복을 해소하려고 두 이름의 입력이나 별칭을 새로 만들지 않는다. 기존 배포 API의 호환성은 별도로 확인하고 요청된 변경 범위에서 적용한다.
- 이 우선순위는 확인된 프로퍼티를 기준으로 중복을 해소하는 규칙이다. 프로퍼티 자체를 조회하지 못했거나 필요한 선택지·동작 계약을 확인하지 못한 경우까지 추측을 허용하지 않는다. 적용한 명칭과 가이드 항목의 대응 근거를 남긴다.

## 타입과 동작 계약

- 화면의 최종 모습보다 확인된 componentProperties의 정의를 우선한다. 독립적인 Bool 프로퍼티는 동시에 표시할 수 없더라도 독립성을 보존하며, 시각적으로 배타적이라는 이유만으로 하나의 enum으로 합치지 않는다.
- componentProperties가 하나의 선택 프로퍼티와 선택지를 정의한 경우에는 그 계약을 표현하는 enum 등을 검토한다. 가이드와 명칭·분류가 겹치면 위 우선순위를 적용하고, 타입은 확인된 프로퍼티의 선택 범위와 항목 간 관계에 맞춰 정한다.
- 독립 입력의 조합에 따라 표시가 겹치면 우선순위와 해제 후 동작을 정의한다. 문서와 기존 합의에서 확인할 수 없는 정책은 임의로 정하지 않는다.
- 기본값이 중요한 설정이나 상태 조합을 숨기면 명시적인 입력을 요구한다. 생략의 의미가 명확한 선택 항목에는 기본값을 허용한다. Figma 인스턴스의 현재값이나 생성 코드의 기본값을 공개 API의 기본값으로 자동 복사하지 않는다. 특정 컴포넌트의 기본값 제거를 모든 기본값 금지로 일반화하지 않는다.
- 표시 설정·데이터·동작의 책임을 구분한다. componentProperties에 없는 식별자·콘텐츠·콜백도 구현에 필요하면 공개 입력으로 제공하며, Model 구성은 위 조합 원칙을 따른다. 업무 API의 요청과 결과 상태 갱신은 호출 화면이 담당하고, 내부 리소스 처리 실패를 업무 실패로 임의 해석하지 않는다.

## 항상 작성: 주석

- 새로 만들거나 수정하는 SDG 컴포넌트·템플릿의 주 선언에는 역할을 설명하는 한국어 Swift 문서 주석(`///`)을 항상 추가하거나 갱신한다. 파일 상단의 작성자·날짜 주석으로 대체하지 않는다.
- 새로 만들거나 변경하는 공개 초기화 함수·함수·모델에는 호출자가 알아야 할 계약을 문서화한다. 입력값의 의미·단위·허용 범위, 입력 간 관계·우선순위·해제 후 동작, 기본값·생략의 의미, 상태 소유자와 콜백 호출 조건·전달 값을 해당하는 범위에서 적는다. 초기화 함수의 파라미터 설명은 기존 `- Parameters:` 형식을 따른다.
- 공개 입력이 어떤 Figma 프로퍼티에 대응하는지 이름과 문서 주석에서 알아볼 수 있게 한다. 확인을 거쳐 명칭·구조를 다르게 표현한 경우에는 그 대응과 이유를 설명한다.
- 동작이 바뀌면 주석도 함께 갱신한다. 호환 API의 주석과 deprecated 안내는 실제 대체 API 및 보존하는 동작과 일치해야 한다.
- 내부 고정 프로퍼티는 이름으로 가이드와 대응시키고, 이름과 코드만으로 불명확한 근거·제약만 주석으로 보완한다. 단순 대입·렌더링을 반복 설명하거나 모든 private 도우미에 형식적인 주석을 붙이지 않는다.

## 항상 명시: 컴포넌트 디자인 버전

- 새로 만들거나 수정하는 SDG 컴포넌트·템플릿의 주 타입에는 적용한 디자인 가이드 버전을 공개 `version` 프로퍼티로 항상 명시한다. 기존 프로퍼티가 있으면 확인·유지하거나 확정된 디자인 버전으로 갱신하고, 없는 작업 대상에는 추가한다.
- 일반 타입은 기존의 `public static let version` 패턴을 따른다. 제네릭 타입 등에서 쓰는 계산 프로퍼티 `public static var version: String { ... }`는 그대로 유지할 수 있다. 버전 프로퍼티에도 컴포넌트 디자인 버전이라는 의미를 문서 주석으로 적는다.
- Figma 디자인 문서·합의된 작업 요구사항에서 해당 컴포넌트의 정확한 버전을 확인한다. 단순 코드 수정·주석 보완만으로 버전을 자동 증가시키지 않는다. 저장소의 최신 배포 버전을 모든 컴포넌트에 복사하지 않는다.
- 기존 버전이 있고 새 디자인 버전 지시가 없으면 기존 값을 유지한다. 신규 컴포넌트이거나 버전이 없는 대상에서 정확한 값을 확인할 수 없으면 확인을 요청하고 미확정 상태를 보고한다. 임의의 `0.0.0`·추측값을 넣거나 버전 명시가 완료됐다고 보고하지 않는다.
- 버전의 원본은 해당 컴포넌트의 `version` 프로퍼티로 둔다. SampleApp의 `SDGGuideDetailView`에 표시하는 대상은 같은 프로퍼티를 참조한다. 샘플 View·상태 모델·내부 도우미마다 별도 디자인 버전을 중복 선언하지 않는다.
- 패키지·앱·라이브러리 배포 버전과는 별개다. 이 규칙 때문에 배포 설정·태그를 변경하지 않는다.

## 최소 코드 컨벤션

- 컴포넌트는 `Sources/ShoplDesignGuide/Component`, 복합 UI는 기존 `Template`, 샘플은 `SampleApp/Sources`의 가까운 구현을 따른다. 인접 코드의 2칸 들여쓰기·이름을 유지하고, 기존 경로·공개 이름의 오타를 이번 요청 없이 정리하지 않는다. 새 SDG 컴포넌트는 기존 `SDG` 접두사를 따른다.
- 공개 API는 호출에 필요한 범위로 제한하고 내부 도우미는 가능한 `private` 또는 `fileprivate`로 둔다. 기존 공개 타입·초기화 함수·파라미터를 변경할 때 실제 배포 여부와 호출부·함수 참조를 확인해 호환 유지·단계적 deprecated가 필요한지 판단한다. 미배포 API에도 무조건 호환 어댑터를 추가하거나 기존 배포 API를 임의로 제거하지 않는다. 디자인에 없는 API 개편을 추측하지 않는다.
- 선택값·입력값·진행률과 이벤트는 기존 호출 계약을 보존한다. 호출부가 소유하는 값은 기존 입력·콜백 또는 Binding 계약을 따른다. SampleApp은 가까운 `@State`·ObservableObject 패턴에 맞추며, 모든 샘플에 별도 상태 클래스를 강제하지 않는다.
- 기존 `SDG.Color`, `.typo`, `Image(sdg:)`, 간격·모서리 반경 토큰을 의미가 같을 때 재사용한다. 새 리소스를 요구하거나 추가하기 전에 가이드의 기존 아이콘·도형·토큰 조합을 확인한다. 고정 규격 수치는 대상 가이드와 대조하며, 없는 토큰을 만들거나 무관한 상수를 일괄 치환하지 않는다.
- 컴포넌트가 커질 때에는 가까운 구현처럼 모델·도우미·미리보기를 분리한다. Model로 입력을 묶는 원칙은 유지하되, 모든 컴포넌트에 동일한 파일 수·중첩 타입 계층·상태 관리 방식·MARK 순서를 강제하지 않는다.
- SampleApp의 제어 항목은 확인된 componentProperties와 공개 입력에 대응시킨다. 데이터·콜백을 위한 예시는 디자인 프로퍼티와 역할을 구분한다. 기존 `#Preview`·PreviewProvider는 대표 외형을 확인하는 최소 구성으로 유지·보완하며, 같은 외형의 조건 조합이나 동작 검증용 Mock을 늘리지 않는다. 샘플의 단순 상태 변경을 실제 API 요청으로 설명하지 않는다.
- 샘플 연결 시 `SDGCatalog`·`SDGViewConfig`·`SDGGuideDetailView`의 기존 등록과 버전 표시를 확인한다. 공용 등록 파일을 다른 컴포넌트의 구현으로 덮어쓰지 않는다.
- 입력 처리와 접근성·애니메이션의 기존 동작을 확인하고 작업 요구사항에 맞게 유지한다. 새로운 강제 종료·무시·보정 정책을 추측해서 추가하지 않는다.

## 작업 마무리

- 확인된 componentProperties·공개 입력·SampleApp 제어 항목을 대조해 누락과 의미 변경이 없는지 확인한다. 가이드의 고정·파생 규격은 내부 프로퍼티와 대조하고, 섹션 이름만을 근거로 불필요한 공개 입력을 추가하지 않았는지 확인한다. 모호한 중복에 componentProperties를 우선 적용했는지 확인하고, 그 대응 근거와 실제 미확인 항목을 구분해 보고한다.
- Model이 데이터와 필요한 디자인 설정을 함께 담는지, 템플릿의 공개 입력이 해당 템플릿의 제약을 보존하는지 확인한다. 하위 설정을 그대로 허용하면 Model을 재사용하고, 선택 범위를 제한하거나 값을 고정하면 템플릿 입력으로 내부에서 하위 Model을 구성하는지 점검한다. 고정값과 콜백·Binding의 별도 계약, 모델 간 중복 설정이나 상태 소유권 변경도 확인한다.
- 독립 입력을 시각적 배타성만으로 합치지 않았는지, 조합·기본값·콜백 계약이 명확한지 확인한다. 주 선언·변경한 공개 API 주석과 정확한 컴포넌트 버전 명시를 확인하며, 문서를 읽었다는 사실만으로 준수를 완료했다고 판단하지 않는다.
- 실제 변경 범위, 공개 호출 계약·샘플 연결을 검토한다. 소스 검토, 컴파일, Preview 렌더링과 실제 앱의 네트워크·입력·상태 전이 검증을 구분해 보고한다. 실행하지 않은 동작은 미검증으로 남기며 Preview로 대체했다고 표현하지 않는다.
- 자동화의 허용 소스 경로와 자동 생성 파일·리소스·프로젝트 설정·인증·게시 권한의 제한은 이 문서로 확대하지 않는다.

## 검토 근거

2026-10-20 사용자 정정으로 공개 API의 기준을 가이드 페이지의 Anatomy·Spec 등 섹션에서 Figma 인스턴스에 노출된 componentProperties로 구체화했다. 기능 화면을 구현하는 사용자가 프로퍼티 패널을 통해 사용법을 파악한다는 이유다. 같은 날 사용자가 `Spec`/`Size` 같은 모호한 중복은 componentProperties를 우선하기로 협의했다고 알려, 별도 판단 요청·디자이너 확인 대기 규칙을 이 우선순위로 교체했다. 가이드 페이지는 세부 규격·동작을 보완하고, 외부 제어가 필요 없는 고정 항목은 내부 프로퍼티로 식별한다.

같은 날의 MCP 확인에서는 가이드 프레임 안의 개별 Avatar 인스턴스를 조회했을 때 생성 코드에 showFace·showIc·showOutline·showRetry·size가 나타났지만, 다른 조회에서는 렌더링 결과만 반환됐다. 생성 코드에서 읽은 일부 값을 원본 프로퍼티 전체 정의로 단정하지 않는 근거다.

같은 날 사용자는 Model을 도입한 목적이 데이터 저장만이 아니라 컴포넌트의 필요한 값들을 묶어 템플릿 사용 시 개별 필드 전달을 줄이는 데 있다고 설명했다. 이를 Model의 공통 역할로 추가했다. 규칙 도입 당시 Avatar의 Model은 userId·imageURL만 담고 디자인 설정은 별도 입력에 있었다. 이후 별도로 승인된 로컬 구현에서 데이터와 디자인 설정을 Model에 통합하고, 사용자가 선택한 대로 콜백은 View에서 별도로 받도록 정리했다.

후속 논의에서 사용자는 SDGSimpleProfile이 Avatar의 Small·XSmall만 허용하는 경우를 들어 하위 Model 직접 주입의 한계를 지적했다. 이에 템플릿의 제약이 있으면 전용 입력으로 범위를 제한하고 내부에서 하위 Model을 구성하도록 예외를 명시했다. 이는 사용자 제시 사례에 근거한 설계 기준이며, 해당 템플릿의 실제 소스 전환을 완료했다는 뜻은 아니다.

다음 Avatar 결정은 Model 통합 이전의 구현 이력이다. 구조체 묶음·Optional 입력·`Spec` 명칭을 다른 컴포넌트의 공통 정책으로 일반화하지 않는다.

- SH-24017 Avatar v2.3.50: 가이드의 독립적인 showFace·showRetry를 Avatar 구조체의 Bool로 보존했다. 두 값이 모두 true이면 Retry를 우선하며 해제 후에는 전달된 Face 설정을 따른다. 호출 의도를 드러내기 위해 두 Bool과 상위 avatar 입력의 기본값을 제거했지만, outline·ic·onRetry의 nil 기본값은 유지했다.
- Avatar는 외부 프로필 API 실패 표시와 재요청 콜백을 받고, 내부 이미지 다운로드 실패는 placeholder로 처리한다. 크기별 두께·아이콘 규격은 내부 계산 프로퍼티로, placeholder는 내부 View 프로퍼티로 표현한다. 코드: [SDGAvatar.swift](../../../Sources/ShoplDesignGuide/Component/Avatar/SDGAvatar.swift). Bool 선택·Retry 우선순위·실패 처리를 다른 컴포넌트에 일괄 적용하지 않는다.
